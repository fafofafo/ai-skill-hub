## ⚠️ picbp 前缀强制规范（2026-10-22 用户定）

**⚠️ 第五要素=主题驱动内容（2026-10-23 用户纠正 picbpskysea）**：四要素只是排版骨架，**画面内容必须由主题派生**——建筑形制/材质/器物/人物身份/场景细节全随主题变，不能写死一个固定场景、只把主题当标题和匾额。用户说「要参考 picbpnew 的方式构图和生成内容」时，指的正是这条：把主题逐项展开成「<由主题派生的 X：例如…>」变量位，再固定「画质/色调/风格」三段收束。骨架 + 内容驱动两条都做到，才算合格的 picbpX。
**⚠️ 第六要素=picbpnew 的「分层构图」（适用于波普/城市/长廊类，工业构成主义除外），不是一段流水描述**（用户已两次以「XX 要参考 picbpnew 的骨架出内容」纠正）：把画面按三层写，缺一层就退化为平铺堆砌——

## 「五元素」验收规则（2026-10-24 用户定，硬性）
用户发**参考图**要求建新技能时，量化核对**只做五元素**：①饱和度（S 均值 %）②R-B（R−B 均值差）③明度（灰度均值，附 V）④柔度（柔度指数：<0.10 很柔 / <0.16 偏柔 / <0.24 中等 / ≥0.24 偏锐）⑤边缘（FIND_EDGES >20/>40 占比）。
流程：参考图 → `python3 ~/.hermes/scripts/img_metrics.py <图>` 取五元素 → 逐条翻译成提示词约束 → 建技能写**五元素验收区间** → 出图复测**只比对这五项** → 文字另用 VL 逐字复核。**不要**在回报里堆高饱和像素、锐度 Laplacian 等其他指标（用户没要就是噪声；内部诊断可用，不对外报）。

**⚠️ 霓虹/夜景主题派生技能的 R-B 平衡口诀**（2026-10-26 picdjgirl/pichkdlj/picrainnight/piclove 四次实测）：R-B 主要由背景霓虹色决定——全蓝紫背景→R-B 过蓝（负值）、全暖橙背景→R-B 过暖（超 +55），**冷暖霓虹各半（人物暖色+背景冷色，或反之）最快收敛**；红/橙为主的人物服饰（红西装/亮片红衣/红衣魔女袍）尤其需要冷色环境光对冲。居家/白领等浅色系人物（米白/深蓝黑）易拉低饱和度，用奶黄/亮橙点缀物（抱枕/风衣/公文包）提 S；同时明度易被室内暖光推超 65%——写「光线柔和适中不过曝」压回区间。

**⚠️ 月光/古风夜景 + 素白衣裳人物的 R-B 平衡**（2026-10-26 picghost 实测）：素白/淡蓝古装人物配冷月背景会让 R-B 直接负值（-10）且 S 掉到 20——不要用「冷月+素白」的写实还原思路，靠**暖烛光为主、冷月为辅**（暖黄烛台/暖色高光大面积）+ 人物加淡粉飘带类暖点缀提暖提饱和，一次措辞到位（v2 即收敛）。

**⚠️ 素雅古装/鬼片主题天然低饱和，达不到 sunny 区间**（2026-10-26 picghost 倩女幽魂实测）：素白衣裳+夜色古宅，image2.5 三版 S 只到 20-25（v1:20.1/v2:23.8/v3:25.0），拉不到 42-55%——同 pictonghua 童话主题结论（低饱和气质主题极限≈25-30）。**建此类主题技能时若用户指定「五元素不变」，先如实说明主题天然低饱和、问是否按低饱和区间验收（30-42%），不要硬拉 N 版消耗额度**；模板本身写高调明亮+暖烛冷月平衡即可。

**⚠️ 全身/远景构图的水景 R-B 平衡难点**（2026-10-26 pichotpoolfull 七版实测）：泳池/海边/天空类**全身图**水面+蓝天冷色占画幅比重大，写「以暖色为主」会被 image2.5 执行过头（红泳装+暖阳+橙伞 → R-B+73~77 过暖超 +55），写「水面占大部分」又过冷（R-B+0~5）——**最稳措辞是「冷暖均衡各占一半」（冷色水面/蓝天与暖色人物/暖阳各半）**，红泳装/暖橙点缀必须保留但冷色占比不能缩到「仅角落」；全身图迭代时先按「各半」写，再按实测 ±15 内微调，一次调一处。

**⚠️ 全身构图/古宅暗调主题的提亮口诀**（2026-10-26 picghostfull 实测）：全身入镜时古宅/夜色等暗调场景背景占画幅大，会把整图明度拖低（全身版 v1 明度 43.9%，半身版同措辞 56%）——**全身版只写一句「高调明亮」不够，必须双强调**：背景句加「整体明亮通透不压暗、无大面积阴影」+ 光线句加「明亮程度高、画面整体偏亮不暗」，一次到位（v2 明度 54.3 贴线收敛）；此口诀适用于一切「全身展示」技能（pichotpoolfull/picghostfull 等 full 后缀版）。

**⚠️ 深夜/夜色主题的明度极限 ≈43-45，与 sunny 明度区间本质冲突**（2026-10-26 picghost2full 深夜武侠 4 版实测）：「深夜/夜色/月下」是 image2.5 强暗调联想词——夜景三件套（high-key 布光+背景明亮不压暗+无死黑）明度仍 36.4、月色如昼 44.7、亮青竹林+密集灯笼 43.3，四版都压不到 55-65。**判定：用户点名「深夜/夜色」场景 + 指定「五元素不变」时，先如实说明深夜主题明度极限≈43-45 达不到 sunny 明度区间，给用户三个选项（接受贴低/场景微调/换亮场景），不要硬拉 N 版消耗额度**——此结论与「素雅古装天然低饱和」同属「主题特性 vs 验收区间」冲突类。

**⚠️ 暗调主题（玄黑/雪山/深夜）提亮提暖四连口诀**（2026-10-26 picghost2full 雪山版 4 版实测）：魔教/武侠/古风暗色人物全身图，只靠提亮双强调不够（S22-25/明度46-47 徘徊）——必须四连：①**服饰换亮色**（玄黑袍→暗红长袍，黑做镶边）；②**场景加暖色光源主导**（大片暖黄灯火/灯笼）；③**光源具体化**（正午阳光/雪地反光，不要泛泛的「烛火微光」）；④**色调方向写「暖色为主带冷色点缀」**（不是「冷暖平衡」也不是「冷色为主」）。实测四连后 S38.0/R-B+36.7/明度55.1 一次全落区间。

**⚠️ 用户明确「其他不变，包括五元素都不变化」= 保持母版区间，不要自动下调**（2026-10-26 pichotpool 实测）：建技能时用户说「包括五元素都不变化」→ 验收区间原样继承母版（如 picsearoad 42-55%），不要因为画面过素就默认套低饱和档；画面过冷过素（泳池/海边水蓝背景 S 30-35/R-B+11-16）时用**「颜色鲜艳三改」迭代画面达标**（高饱和正红泳装+暖橙点缀+主标题红色填充+饱和度拉满不脏不灰，实测 3 版收敛 S39.6 贴线合理），而不是改区间。

**⚠️ 手绘画风（米白纸底/墨线/低饱和复古色）对齐 sunny 区间的配方**（2026-10-26 picbpwhj/picgirlwhj 对齐 pichotpoolfull 三版收敛实测）：复古手绘画风天然低饱和+高边缘（v1.0 S34.9/柔度0.258/边缘25.34），用户要「五元素调成和 XX 一致」时——**验收区间直接对齐目标技能（通常就是 sunny 42-55/…/边缘10-20）+ 提示词按三处收敛配方改**：①配色从复古自然色（湖水青/陶土橙/炭黑）换成**鲜艳复古色（朱红/靛蓝/翠绿/芥末黄）**+「高饱和明亮、饱和度拉满、不脏不灰」提 S；②柔化组合词必须带 **no ink outlines**（墨线描边持续拉高边缘，光 soft edges 不够）；③美女版比纯场景版更难提 S（肤色+米白纸底占面积）——**背景微缩世界用大面积鲜艳色块平涂**是最有效手段。实测：纯场景版 S38.9、美女版 S38.3（都贴线合理判定），柔度/边缘都压回区间。

**⚠️ 婚礼/喜庆主题天然 R-B 过暖（红元素主导）**（2026-10-26 picbpwhj/picgirlwhj 婚礼主题实测）：主题元素带红（花轿/红盖头/红灯笼/喜服）时 image2.5 会把朱红推到主导，R-B 直接 +82~92 超 +55 上限——**不要只靠「配色含冷色」期望自动平衡，必须显式写主从关系**：「靛蓝/翠绿/芥末黄为主、朱红仅作局部点缀，背景大面积靛蓝翠绿冷色块平衡画面，朱红只用于 X 等局部强调」；实测一次收敛到 +55~56（贴上限），再用提亮（米白纸底占比大+高调曝光）把明度拉回区间（冷色块多会压低明度）。

**⚠️ 用户指定「饱和度低一些」= 验收区间按用户要求下调，不套 sunny 区间**（2026-10-26 pictonghua/picafternoonwind 两次实测）：触发时机有两种——①**建技能时点名低饱和**（pictonghua 童话淡色系）②**初测后追加**（picafternoonwind v1 已按 sunny 区间 S42.7 达标、用户说「饱和度低一些」）。②走**风格迭代调整流程**（就地 patch 技能 v1.0.0→v1.1.0，不是重建）：五元素表饱和度区间改为 **30-42%**（其余四项仍按 sunny 区间）+ 画风定义色彩行 + 模板配色句 + 派生规则 + 经验小节五处同步改，家族索引行标注「低饱和版」，同步两端。提示词写法：**低饱和度但色彩鲜艳（明确色相、多彩不灰白——雾蓝/奶油黄/干枯玫瑰粉/鼠尾草绿等温和调）** + 光线句「光线柔和适中不过曝」防明度被淡色推超 65%；点缀色提 S（红蘑菇帽/明确色相斗篷）只在淡色系单色化时需要。收敛速度：**多彩低饱和措辞 + 不过曝守卫一次出图即可压到 ~S32**（picafternoonwind S42.7→32.4 一次达标，不必像 pictonghua 淡色系那样三版试）——image2.5 低饱和极限 ≈ S 25-30，达到 25-30 且其余四项落区间即视为达标，勿强求 30+；低饱和+高调明亮是矛盾组合，明度易被淡色推超 65%。

**⚠️ 独立模板验收例外**（2026-10-26 picfacebustketball 实测）：独立模板（主题驱动、非 sunny 系画风）**不以 sunny 五元素区间为准**，以模板自身设计意图为准——如「强硬街头赛事印刷拼贴」模板明确要求「中等偏低明度、主色厚实、黑白强反差、浅纸底」，实测 S26.8/明度40/边缘24 正是模板要的效果，按 sunny 区间判反而错判失败；验收时先读模板的明度/饱和/对比意图句，意图本身就是验收线。**浅纸底/呼吸空间等理想化描述 image2.5 难生成**（实测加「浅米色纸底占三成」仍出重黑），不必强求、不以「纸底占比」作为验收项。

**⚠️ 「调成和 X 五元素一致/完全一致」= 对齐参考技能工作流**（2026-10-26 多技能实测：pictonghua/picrussiagirlsolider/pictry→mvglassout、picbpwhj/picgirlwhj/piccat/picbpbot→pichotpoolfull）：用户说「把 A 调成和 B 五元素一致」时——
- **目标 B 是 MV 技能时，基准取它的配图技能**（mvglassout 无验收表 → 取 picglassout 实测 S35.9/R-B+17.4/明度45.5/柔度0.137/边缘11.75），不要从 MV 正文找；
- **「一致」分两档**：区间对齐（验收区间改成参考技能同款，如明度 55-65→45-55）vs **完全对齐**（验收目标=参考实测值 ±3，用户说「可以牺牲别的元素」=画风表达可妥协、数字优先）；
- **跨画风对齐有模型能力边界，先如实说明再给选项，不要硬拉 N 版**：数字插画 3D 渲染对齐 Loish（S 拉不到 35.9，夜景冷蓝压制极限 28-31；柔度/边缘拉不到 0.137/11.75，3D 渲染天然锐利）；黑灰金机械配色对齐 sunny（S 极限 20-25）；R-B/明度通常可对齐，其余按画风差异接受。选项=①接受最接近值定稿 ②换配色/画风再试 ③改回原验收——用户拍板后回填「接受 vN 当前值」并固化收敛措辞；

7. **出图后视觉模型复核**（2026-10-16 起常态）：测试图/交付图出图后用硅基流动 Qwen3-VL 复核 5 项——主色调氛围、标题文字是否正确清晰、主题元素是否到位、右上角 FAFO 标注、质感风格是否达标；复核通过才发频道。视觉 API 用法见 llm-api-integration。**⚠️ 大图先压缩再送，宽 ≤512 才稳**：1.8MB+ 的 PNG 直接 base64 送 siliconflow 会 read timeout；实测 720/800 宽 + quality 80-85 仍超时（两次都失败），缩到 **宽 ≤512、JPEG quality 80-85**（base64 约 100-150KB）才稳定成功——超时先缩到 512 再重试，别原图或 720 宽重发。标题等文字复核单独再问一次（主分析 max_tokens 常截断，正文尾部文字被切断）。**小号底部署名要裁剪成特写再问**：直接成全图问，模型对底部小字会误读（实测同一张图全图读成 ZHAZHU，裁剪后读成 AIHD——各次结果不一致就说明该处字形不稳，需换图或改提示词）——用 PIL `im.crop((0, int(h*0.86), w, h))` 裁底部 12-14%、放大到宽 700-760、JPEG quality 90 再问「逐字读出所有可见文字，有无遮挡或错字」，结果比全图可靠得多。**底部系列署名也要逐字核**：`AIXZD ZHAPU PROJECT SERIES` 曾出现首字母错成 `ZHXZD`（英文小字 AI 易错），复核提问里显式要求「底部系列署名读什么」。**⚠️ 视觉 API 偶发 HTTP 500 / read timeout 是瞬时错误**（2026-10-20 多次实测）：同请求直接重试（最长 200s 超时窗内）通常即成功，不是账号/模型/quota 问题，别改参数别换图。**⚠️ 视觉 API 返回 402 是余额/额度问题，与 500/timeout 瞬时错误不同**（2026-10-24 实测）：402 不要反复重试（重试仍 402），直接降级交付——图 + 五元素照发，注明「VL 暂不可用，文字请你扫一眼」，余额恢复后可补复核。**⚠️ VL 复核通道降级顺序（2026-10-28 实测）**：唯一主通道=vision_check.py（硅基流动 Qwen3-VL-32B）；内置 vision_analyze 走 coding plan 通道不支持视觉（UnsupportedModel）、火山 ark 推理 key（~/.arkcli/config.yaml）无视觉模型权限（doubao/Qwen-VL 均 404）——都不是可用备选，别为找通道反复探测消耗轮次。**全通道不可用时五元素照跑照发**（img_metrics.py 纯本地无外部依赖）：图 + 五元素结论 + 一行「VL 复核暂缺（通道欠费/不可用），充值后可补」交付，并给是否出 v2 的选择——视觉复核是保质量动作，不是交付前置门槛，别为等通道阻塞交付。**⚠️ 别凭「模型已升级、可以直接看图」就向用户承诺能直读图**：先跑一次实测（`vision_analyze` 或硅基流动脚本），确认通了再宣称；实测不通时如实说「内置工具仍走旧后端，我用硅基流动 Qwen3-VL 复核，结论一致」，然后直接走脚本路径交付——用户关心的是复核结论，不是哪条通道。
8. **⚠️ RunningHub 提交失败≠脚本问题，重跑即可**（2026-10-16 多次实测）：提交阶段报 `'NoneType' object is not subscriptable`（提交重试 N 次后仍失败）、或 300s 任务超时，都是服务端队列满/限流（TASK_QUEUE_MAXED 421）——直接**重跑同一 t2i 命令**（有时需重试 2-6 次），不要改脚本；**出图任务一律后台跑**（background=true + notify，循环 3 次 + sleep 20），前台只轮询——限流时段单张图也会连续两次前台 420s 超时，前台死等纯浪费。**⚠️ 同批连续出图多张后遇 605（NOT_ENOUGH_BALANCE）= 余额耗尽，不是队列**（2026-10-26 建技能必测批量出图多次实测：一个批次建 4-5 个技能、每技能测 2-4 版，币消耗快，中途报 605 属正常）——605 是**非瞬时故障**，重试循环无效（重试 6-14 次仍 605）；探测用 `curl` 提交一次最小请求看返回码区分（code 0=正常/605=余额/421=队列）**——探测必须复刻 runhub_img.py 的 submit() 请求形状**（`/task/openapi/ai-app/run` + webappId + apiKey + nodeInfoList 字段，2026-10-26 实测：拿裸 prompt 打其他 t2i endpoint（如 /api/v1/task/t2i/async）会返回 412 TOKEN_INVALID 误导判断，换成脚本同款请求才看到真实 code 421），**605 立即停下告知用户充值，不要消耗重试时间**；**421 队列满可能持续多个后台重跑周期**（同批两任务并行都 8 次重试失败）——确认 421 后继续排队重跑同一命令即可，**同批图串行排队，别开两个以上并行后台 t2i 互相加重限流**；充值后重跑同一命令通常一次成功。批量建技能时把出图预算按「技能数×3 版」估算，避免中途卡死。
9. **⚠️ 改「轮廓柔和/边缘柔和」不能只写中文模糊词**（2026-10-19 picbpfirework 实测）：单句「每个物体的轮廓边界都柔和过渡」对 image2.5 几乎无效，复核仍是犀利硬边。有效写法=**英文风格关键词 + 具体羽化/晕染机制**，如：`soft edges, painterly brushwork, feathered outlines, everything blends softly with glow and gradient transitions, no hard sharp contour lines, no crisp vector edges` + 中文「边缘如水彩晕染般柔和」「以柔光晕过渡不突兀」「标题带柔和光晕和温柔投影（而非利落描边/清晰投影）」。用户要「柔和」时优先用这套组合词，别指望单条中文描述生效。
10. **⚠️ 写实人物主题过审措辞**（2026-10-19 picsunny 实测）：image2.5 内容安全审查（errorCode 1501「安全审查未通过」）会拦「紧身/身材线条/汗珠泛光」等身材细节描述——写实人物海报避开这些，改用「宽松运动衣/自然姿态/晨跑拉伸」类健康中性措辞即可过审。渲染失败报 1501 时先改措辞重试，不是脚本/模型问题。**⚠️ 泳装/比基尼直接触发 1501（2026-10-22 picbpfastion 实测）**：即便写成「端庄克制、非暴露的时装泳装」仍被拦（两种不同措辞均 1501）——写实人物要泳装时改为「夏日度假时装/露肩连体裙装+薄纱罩衫」类措辞即可过审；被拦后勿反复用泳装词重试，直接换度假时装表述。
11. **⚠️ 高文字密度模板（多人物社论/群像等）必须内嵌「文字约束」段**（2026-10-20 piclovesunny 实测）：image2.5 在多人+排版融合场景（重叠/蒙版/环绕装饰字）会生成**形近乱码伪汉字**（如「潮」变「虐」字形扭曲），中文越密越易触发。模板里单靠「避免乱码漏字」一句不够——必须显式写：**所有可见中文必须清晰规范、笔画完整，禁止模糊扭曲/形近错字/伪汉字；主标题与关键文字逐字准确；环绕/装饰性文字如有模糊风险一律用无字图形、色块或符号替代；宁可少放文字也绝不出现错字**。复核时把「有无乱码字形」列为必查项（群像图尤甚）。
12. **⚠️ 结构化几何指令（等距透视/严格对称等）对 image2.5 遵循度低，会退化为常规线性透视**（2026-10-20 picbpvtr 实测）：模板写「正视等距透视（isometric）、无镜头畸变」，复核仍判为「近大远小的一/多点线性透视」（one-point perspective）——地标建筑、砖墙栏杆的消失线全部汇聚，符合单点透视而非等距。这是模型能力边界，不是提示词写错：等距是硬需求时用文字再强调「45° 俯视、三向等角、平行线不汇聚」，否则接受线性透视并把「无畸变」作为达标线（两者都无镜头畸变）。
13. **⚠️ 镜头几何类指令（14mm 超广角/桶形畸变/严格对称）同样遵循度低**（2026-10-23 picbpbookroom/picgirlbookroom 实测）：把「14mm 超广角畸变/边缘拉伸/透视夸张/左右严格对称」写到句首并重复强调，出图仍是「中景平视、视觉平衡但不严格对称、无明显畸变」——与规则 12 同属模型能力边界。**判定：超广角是硬需求时不要指望提示词解决，改换支持镜头参数/图生图的 app，或接受「纵深层次强」作为达标线并如实告知用户畸变未生效**；不要为同一张图反复加词重跑（跑两次无变化即定性，别把额度耗在模型不会做的事上）。
14. **⚠️ 同一主题批量测多技能（≥3 个）的标准打法**（2026-10-23 六技能实测）：①每技能写一段独立提示词文件 `/tmp/<技能>_<主题slug>_prompt.txt`，主题只进提示词、不进技能模板；②**单个** background 任务里 `for n in <技能列表>` 串行出图（每张 3 次重试 + sleep 20），6 张约 8-10 分钟——别开 N 个并行任务，RunningHub 会限流；③复核用一个脚本逐张问 API，**每张限「只列 4 点、250 字内」并把结果写文件再 read_file**：长回答会让 process log 尾部整段截断（max_tokens 撞顶时最后几问直接丢失），分文件读也避免一次读超长；④复核四项固定=主体元素/色调光影/左上主标题逐字/右上+底部署名+乱码，**主标题逐字是硬指标**（六字中文标题实测 6/6 全对）；⑤回复用结果表（技能×画风×文字×瑕疵），只对「文字错/署名丢」提重跑，画风微漂移如实说明不反复消耗额度。
15. **⚠️ 画面品牌文字三条生效写法**（2026-10-23 六技能实测）：①**底部系列署名必须显式写**——提示词不写「画面底部居中加入小号文字『AIXZD ZHAPU PROJECT SERIES』」时模型基本不生成，多条模板实测底部空白；②**右上角要纯中文品牌名必须加双重否定**——写「右上角粗体字标注：FAFO工作室」时常被替换成自造英文 slogan（如 ART FILM LIFE AND BEYOND），改为「画面右上角用粗体简体中文标注：FAFO工作室，中文汉字，不要英文，不要其他标语」才稳定；③**主标题（左上超大艺术字）是三者中最稳的**，几乎不出错，若底部/角落小字与主标题冲突，优先保主标题。复核时把「底部署名逐字读」列为独立检查项，别只看标题与 FAFO；④**署名位置必须钉在干净区域**——只写「画面底部或角落」时，密集结构背景（钢架/管道/齿轮/城市堆砌）会把小号英文串切碎或压变形（实测 AIXZD 被读成 AIHD/ZHXZD）。有效写法：把署名句改成「画面最**底部中央的深色平整区域**，以不抢眼的方式加入小号品牌文字「AIXZD ZHAPU PROJECT SERIES」，**完整清晰不被遮挡**」，实测一次修好。元素越密的画风越要用这条。
16. **⚠️ i2i 图生图技能（picupfoodout 模式，2026-10-26 实测）**：用户提供「基于上传图编辑」模板（如保持原图不变、只做局部特效）时建 **i2i 技能**——默认工具=全能 image2 图生图 app `2047883048150110209`（~0.108 元/张），**不能走文生图 app**（image2.5 sunburst 是 t2i 专用）；验收**不以五元素区间为准**（特效图以「保持原图+特效效果+无卡通感」为准），跑通即可交付；用户发图无文字时优先推断为刚建 i2i 技能的测试素材，直接跑 i2i；i2i 提交偶发失败（NoneType 重试）在余额足时多次重试会成功（实测重试 14 次后提交成功），不用改模板。

1. 用户发来 image2.5 模板 + 主题，要求「按原格式重新输出一份」→ 先按模板产出主题改写提示词。

4. 回填本索引表。**⚠️ 表格追加行用「锚点行+下一行开头」做 old_string，new_string=锚点行+新行，不要用单行替换**（2026-10-22 实测：old_string=某一行、new_string=新行会把旧行覆盖掉——回填 picgirlghost2 时误删了相邻的 picgirlwood 行，需手动恢复）；回填后 `grep -c` 确认相邻行仍在，并同步 learn 副本（cp + diff）。**⚠️ 插入前判断「该行是否已存在」必须用行前缀匹配 `any(l.startswith('| <技能名> |') for l in lines)`，不要用 `'<技能名>' not in '\n'.join(lines)`**（2026-10-25 实测：同一文件里的历史叙述段（删除规则示例等）会包含技能名文本，子串判断恒 False → 插入被静默跳过，之后 grep 发现表行没进去）。选型依据键值对同理：先 grep 确认旧锚点真的存在再 replace，锚点不存在时 replace 静默无操作，别等输出「已补」就以为加上了。

## 文本风格→新技能流程（picbpsky/picbpdarkblue/picbpnature 模式，用户 2026-10-16 定）
用户直接发一段风格描述文本（画风/光影/色调关键词，可能带「以上内容是 image2.5 的提示词」）要求做新技能时：
1. 按用户原文拆出**画质/色调/风格**三段特征（用户常已分段给好，直接结构化照抄），必要时用视觉模型实测验证（同参考视频流程第 2 步）。
2. **先判断模板性质**（2026-10-16 修正，三种情形）：
   - 风格描述文本（无独立结构指令）→ **框架替换型**：新技能提示词只替换画质/色调/风格三段，其余结构（左上主标题/右上建筑/中部街头元素/底部巨型元素/配色段落/署名/最终输出句）全部照搬 picbpnew——用户明确要求，自创场景结构会被纠正（picbpclean 初版被纠正过）。
   - 自带完整独立结构的模板（如 picgta6 身份重绘）→ **独立模板型**：直接保留用户原文模板，套 picbpnew 拼贴结构反而违背模板意图；同时检查模板是否排除文字/水印/真实 Logo——排除则默认不加 FAFO 标注。**⚠️ 独立模板型仍可能被用户拉回 picbpnew 骨架**（picbpeat→picbpfood、picbpfastion/picbpwood 多次实测）：用户先给自包含完整模板（含「主标题在上方雾气留白内+角落页码+除菜名页码外无文字」等特殊规则），建完测试通过后用户问「XX 生成方式是不是参考 picbpnew」或直接命令「XX 要参考 picbpnew 的生成方式」「XX 也一样参考 picbpnew」——**问句和命令句都是「偏好统一到 picbpnew 骨架」的信号**。对齐时**只换骨架（左上超大主标题第一焦点/右上或主体区域/中部元素/底部巨型元素/配色段落/系列署名 AIXZD/末尾 FAFO），画风/器物/禁令内容原样保留**；用户给的多段式详尽模板（九段式等）也要收缩成该骨架，不是把旧骨架留在里面加新段落。建独立模板型技能时可在技能里预置一行「与 picbpnew 骨架的差异点」，用户一要求即快速对齐。**⚠️ 独立模板可能自带「输出模式」条款**（如「收到『改成专属完整提示词』的任务时仅改写提示词、不执行出图；未填的必填项应先询问」）：建技能时整段保留并写进「触发」，否则未来会话会直接出图，违背模板约定。**⚠️ 模板比例与默认 app 不符要主动说明**：默认 app 固定输出约 3:4（见共享规则 3），模板写 2:3／9:16／16:9 时出图前说明「默认工具产出 3:4，严格比例需换支持 ratio 的 app」，别默默交一张 3:4 当 2:3。**批量新建**：用户会连着发多个「新技能 X，提示词：<完整模板>」——逐个独立建（各自模板照抄、**不做骨架互相统一**），每个都走同步两端 + 回填索引，索引行统一标「（独立模板）」提示后来者不要套 picbpnew 骨架。**⚠️ 独立模板批量转 picbpnew 骨架版=新建平行技能，不是改名**（2026-10-22 实测 picbpcar/picbpmanstory/picbpbookface/picbpfgcity）：用户说「按照 picbpnew 的方式，训练新技能 picbpX」时——①原技能（piccar/picmanstory 等）**保留不动**，新技能用 picbp 前缀名；②骨架定义固定=「主题嵌入开头 + 左上超大主标题 + 底部系列署名 AIXZD + 右上 FAFO」，**画风/器物/禁令内容原样保留**（同「拉回骨架」规则）；③索引行标「（picbpnew 骨架）」，与「（独立模板）」区分。**⚠️ 用户批量给的技能名可能自相矛盾/含乱码**（2026-10-22 实测「picbpccar、picbpcar、pic吧【fgcity」）：同一批里出现两个几乎相同的名字、或带乱码字符时——先 clarify 逐个确认（哪个是真名、哪个笔误、是否有第二个提示词），确认清楚再动手，别猜着建一堆错名。**⚠️ 骨架升级后必须同步检查引用它的 MV 变体差异表**（2026-10-22 mvgirlfood 实测）：picgirlfood 从独立模板升 v1.1.0（picbpnew 骨架）后，mvgirlfood 的「与 mvbpnew 的唯一区别」表仍写旧描述「菜名+页码唯一文字」——MV 变体正文的配图描述是复制时的快照，配图技能改骨架/描述后不会自动更新，需逐个 grep 引用方（`grep -l <技能名> ~/.hermes/skills/creative/mv*/`）并同步差异表，否则 MV 技能指向过时的配图规则。
   - **完整英文绘画/艺术风格描述（如 "Song-style ink shanshui on aged silk..."）→ 默认仍是框架替换型**：画质/色调/风格段用英文原文（可加「采用古人画笔绘画的方式：毛笔蘸墨、皴擦点染」类绘画方式强调），结构照搬 picbpnew——用户对 picbpssh 的最终定稿是「画质/色调/风格用原本提示词，其他内容参考 picbpnew」；若用户明确说「保留原文、不套结构」才做独立模板。判定信号：描述是自洽完整的一段艺术风格句（含画法/材质/构图/配色），非碎片关键词。
3. 创建技能（creative 类）：frontmatter 的 description 首句自包含触发词（Use when …），**必须 ≤60 字符**——超长会创建失败（报 `must fit the 60-char budget`），先压缩再提交；含「参考视觉特征」小节（用户原文规范化）、模板结构、固定标注、交付规则、出图命令、经验（含与 picbpnew 三处差异、结构来源注明）。
4. **覆盖已有技能**（用户说「覆盖原来的技能 X」）：不改名，把 X 的 SKILL.md 整体替换为新风格内容（frontmatter name 不变），正文注明「<日期> 用户覆盖原<旧风格>版」。同步 + 测试照常。**⚠️ 覆盖前先想旧风格是否还想留**（2026-10-20 picbpgd 深黑壁纸版被覆盖为纪实摄影版实测）：覆盖是破坏性的，旧风格内容会永久丢失——若旧风格是独立可复用资产（用户曾用它出过图、家族索引有独立描述），**主动提出改名另存旧版**（如 picbpgd 深黑壁纸版 → picbpblack）再覆盖，别等用户问；用户明确只要新风格不保留旧版时才直接覆盖。
5. 同步两端（真相源=default 总频道库 `~/.hermes/skills/`，learn 本地副本）：新技能直接写 default 后 `cp default→learn`；**别依赖 sync 脚本**——`sync_learn_skills.py` 会静默跳过「learn 进化版」技能（含 picgirl/runninghub-marketplace-search 等），写完必须 `diff` 两端验证，learn 落后手动 cp（见经验小节）。
6. 测试出图（常用「遥远的她」等歌名做跨风格对比）+ 视觉模型复核 5 项后发频道，回填索引表。

## 技能重命名流程（2026-10-16~20 实测 picbpblue→picbpsky / picbphjq→picbpkb / picbpgta→picgta6 / picbpsummer→picbpfirework / piclzq→piclove）
**重命名=纯改名+引用同步，不出测试图（用户 2026-10-26 定）**：重命名不改技能内容与已测结论，不需要重新出图验证；测试图只在画风/模板有实际改动时才出。
0. **先校验目标名符合双系命名约定**：场景向 `picbpX`/`mvbpX`，美女向 `picgirlX`/`mvgirlX`，无连字符。用户给的名字常缺 `bp` 段（说「picghost2」实为 picbpghost2、「picbpteal」实为 picbpghost2 的旧名）——**按约定补全后再执行**，并在回复里点明「你写的是 X，我按约定命名为 Y」；拿不准时先 `hermes skills list` 核对是否已有同族技能。中途建错名要立刻删干净（default+learn 两处）再建正确名，别留半成品。
1. 创建新名技能：内容复制原技能，改 frontmatter name + 正文标题 + 家族索引行，正文开头注明「原 <旧名>，<日期> 用户重命名为 <新名>」。多个重命名可一次批量创建（operations 数组）。
2. 删旧技能两处：skill_manage delete（learn，**每个 delete 必须是独立 call**，不与 create/patch 组合，否则报错）+ `rm -rf ~/.hermes/skills/<类别>/<旧名>`（default）。
3. **全局替换其他技能里的旧名引用**：`grep -rl <旧名> ~/.hermes/skills/ ~/.hermes/profiles/learn/skills/`（**范围跑两个库全部文件，不只 creative/ 目录**）→ 替换（related_skills、开发来源、差异对比、技能族清单、**skills/.usage.json、.curator_ledger.jsonl 元数据、脚本注释（如 lyrics_segment.py 里「供 picbp 逐段出图」）都会引用旧名**，漏一处就指向不存在的技能）。替换后 `grep -c <旧名>` 确认 0 残留。**⚠️ 带连字符技能名（pic-bp→picbp）可 naive 全局替换**：连字符不构成其他技能名的子串，无 picsun/piczh 那种子串冲突，但也按全库 grep 复查元数据与脚本。
   - **⚠️ 旧名是其他技能名的子串时必须用正则保护**（2026-10-20 picsun→picgirl 实测）：`picsunny`/`mvpicsun`/`picsuny2k` 都含 `picsun`，naive sed 会把它们改坏。用 Python 负断言：`re.sub(r'(?<!mv)picsun(?!ny|y2k)', 'picgirl', t)`（前不跟 mv、后不跟 ny/y2k）。替换前先 `grep -rl` 列出目标文件，替换后 `grep -rn <旧名>` 全库复查，残留只允许新技能自己的「原 <旧名>」历史注记。
   - **⚠️ 姐妹名前缀保护**（2026-10-25 picgirlinside→piczhgirlin 实测）：`picgirlinsidefree` 以 `picgirlinside` 为前缀，naive 替换会把姐妹名一起改坏——同样用负断言 `re.sub(r'picgirlinside(?!free)', 'piczhgirlin', c)`，替换后 `grep -rE 'picgirlinside(?!free)' -P` 复查确认只剩姐妹名自身。**in/out/free 后缀兄弟技能族**（piczhgirlin/out、picy2kgirlin/out、picglassin/out、picgirlinsidefree）里改名时必查该族其他成员有没有被误伤。
   - **⚠️ MV 变体名保留、内容引用更新**：配图技能改名时（picsun→picgirl），对应 MV 变体技能名（mvpicsun）**不改名**，但其正文里的配图引用（「配图用 picsun」）要同步替换为 picgirl——否则 MV 技能指向不存在的技能。
   - **⚠️ 带数字后缀的家族批量改名必须倒序替换**（picbpreal3/picbpreal2/picbpreal 更名实测）：替换顺序按旧名长度倒序（先 `X3`、再 `X2`、最后裸 `X`），否则裸名规则会先吃掉前缀，把 `X2` 变成 `新名2`，留下 `新名2` 这种不存在的技能名。用 Python 对 `<旧名>(?![A-Za-z0-9])` 逐个替换，且每对替换独立成对执行、不要串成一条 regex。
   - **⚠️ 新名与既有技能名形近时单独验证**（picbpbookroom ↔ picbpbackroom 只差一个字母）：改名前后都对该「形近兄弟」跑 `grep -c <新名>` / `grep -c <旧名>`，确认兄弟技能正文没被污染——通用词边界断言防不住「用户给的新名恰好是另一技能名的近邻」，只能靠点名核对。
   - **⚠️ 替换会污染历史字符串，改完必须回查并还原**（同一批改名实测）：`/tmp/<旧名>_backup.md` 备份路径、正文里「原 <旧名> 版」历史注记、选型依据里「<旧特征>→<旧名>」的键值对都会被一起替换掉——备份路径被改会指向不存在的文件（未来恢复失败），键值对里旧风格描述与新旧技能对不上。**做法**：替换后 `grep -n <新名>` 逐条读关键行，把备份路径与历史注记还原成旧名，并把过时的键值对（如某技能早期风格）改成当前真实描述。
   - **⚠️ learn 副本要跑同一套替换**：先改 default 全库不代表 learn 干净——learn 下的技能副本各有自己的「技能族」清单，需对 `~/.hermes/profiles/learn/skills/` 再跑一遍同样的倒序替换；跑完 `grep -rn <旧名>` 复查，**只允许 Hermes 内部台账 `.usage.json` / `.curator_ledger.jsonl` 残留**（历史记录，手改会破坏一致性）。
   - **旧名不存在时按语义找最接近的现有技能**：用户说重命名一个库里没有的名字（如「picsuny」实际是 picsun）时，用技能清单核对最接近的现有技能、按父技能关系确认（picsuny2k 的父系是 picsun），确认语义吻合再执行，不要照字面建不存在的新名。
4. 再跑 sync 到 default，diff 两库确认一致。

## 风格迭代调整流程（2026-10-20 picbpy2k 四版实测：绿色→加XP元素→去XP元素→Frutiger Aero）

2. **经验小节加一行版本演进**：v旧→v新改了什么（「v1.1.0 加 Windows XP 元素+蓝白主调 → v1.2.0 去掉 XP 元素」），最终版核心记忆点 + 禁止项并列写明，避免下次会话误用旧版风格词。

4. **用用户指定的同一测试主题重新出图**（如 picbpy2k 三次都用「老范我要结婚啦」）+ 视觉复核 5 项，复核**把「新方向禁令是否遵守」列为必查项**（如「是否完全没有 Windows 界面元素」）。
5. **⚠️ 调亮画面：只写「明亮通透/浅阴影」不够，且分两类场景**（2026-10-20 picbpkt/picgirlkt、2026-10-22 picbpghost2 实测）：

6. **双系技能（场景向 picbpX + 美女向 picgirlX）亮度等级要对齐**（2026-10-20 picbpkt/picgirlkt 实测）：用户问「以后用 X 是不是默认都高亮」意味着期望两技能默认一致——只调亮一个会留下不对称；任一改亮度时把同画风兄弟技能也同步升级到同一亮度标准（如 picbpkt v1.2.0 对齐 picgirlkt v1.1.0 同为高亮版），并在各自经验小节记版本对齐。

9. **⚠️ 「颜色鲜艳一些」的标准三改 + 「设为默认」要双系同步**（实测饱和 13.2%→31.4%）：用户嫌图偏灰时改三处——①配色句换成「高饱和正红、亮橙、工业黄为主力色块，纯黑纯白工业灰退为背景基底与结构骨架，色彩干净纯粹不脏不灰、饱和度拉满」；②主标题句加「字面填充高饱和亮红色」；③禁止项补「脏灰浑浊色」。副效应是明度自然压低一档（画面更有力），不必额外调。实测：饱和 13.2→31.4%、高饱和像素 11.35→28.39%、R-B +6.3→+41.1。用户说「把这个设为默认」时，**独立模板与其 picbpnew 骨架版必须同时改默认**（两个 SKILL.md 主模板 + description/tags + 量化主表 + 家族索引行），旧冷峻配方降为「冷峻模式」可选——只改一个会被追问「默认都要先颜色」。

## 参考 B站视频→视觉风格学习流程（2026-10-17 实测《Sunny Bread》）
用户发 B站链接要「学习画质/画风/色调」（内容不管）时：
1. **解析短链拿 BV 号**：`curl -sL <b23.tv/xxx>`（带浏览器 UA）看 final_url 里的 `BV1...`；或直接 api.bilibili.com。
2. **拿元信息+封面**：`curl -s -A "Mozilla/5.0" -H "Referer: https://www.bilibili.com/" "https://api.bilibili.com/x/web-interface/view?bvid=BV..."` → data.title/owner/pic（封面 URL 直接下载，B站图床无需鉴权）。
3. **下载视频抽帧**：`/x/player/playurl?bvid=...&cid=...&qn=64&fnval=1`（cid 从 view API 的 data.cid 拿）→ durl[0].url 直接 curl（带 UA+Referer）→ ffmpeg 抽 2-3 帧（-ss 3 / 15 等不同位置）。浏览器路径同样可行：browser 打开视频页等 `window.__playinfo__` 的 data.dash.video[0].baseUrl（带 Referer+UA）下载。**⚠️ 指定时间点（如 318.1s）抽帧必须下载足够字节**（2026-10-22 实测）：Range 只下头部 8MB 后 `ffmpeg -ss 318.1` 会 HEVC 解码失败（partial file / Invalid NAL unit）——字节不够覆盖目标秒；按「目标秒 ÷ 总时长 × 全片估算体积」放量（360P 8 分钟片下载 14.5MB 即覆盖 480s 成功），或直接 Range 0-50000000 整段拉下再 -ss 抽帧。
4. **视觉模型分析**（Qwen3-VL）：封面+多帧分别问「画质/画风/色调/光影笔触/可复刻特征」，内容不管。
5. **⚠️ 多帧分析放后台**：封面+2-3 帧 = 3-4 次串行 API 调用，每次最长 200s，前台会超 600s 上限——必须 background=true + notify 再轮询，勿前台等。
6. **反向推理提示词→出图验证闭环**（2026-10-17 用户常要求，Sunny Bread/Summer Time 均走）：把风格档案倒推成一段**可复刻的完整提示词**——画风/色调/光影三段按实测特征写（不要拼贴结构），内容场景按主题合理拟（面包→金黄面包+热牛奶+阳光窗台；夏祭→华丽少女+灯笼+烟火），用 Image-2.5 出图，视觉模型复核「复刻效果如何」通过即交付。
   - **视觉模型不可用或要数值化时走像素量化**：用户发参考图要「反向解析 image2.5 提示词，不要管画面内容，只要画风」时——跑 `visual-production-qa/scripts/analyze_style.py`（纯 numpy+PIL）拿色温 R−B、饱和度、明度、明暗对比、暗部/高光占比、色相分布、锐度、颗粒，同系列多张取均值当基准；风格段固定 8 句（画风/调色饱和/明暗结构/光影/质感/景深/色温氛围/标注），**主体与场景单独一句**，换主题只改这一句即「一套风格复用到任意主题」。出 1 张测试图后复测：色温 ±10、饱和 ±0.08、对比 ±0.03 内算还原；明度或暗部占比偏离基准 >10 个百分点 = low-key 强度不对，改措辞重出。多版对比时把实测数值列成表选版，比主观描述有效。
   - **⚠️ image2.5 饱和度可控性弱，是反向解析的主要失真源**：点名金黄/橄榄/砖红等多种强调色会把平均饱和度从 0.45 拉到 0.7+；低饱和必须显式写「去饱和 40-50%、灰调哑光、不鲜艳不油亮、绝不出现高饱和红橙/荧光色/冷蓝紫」，实测可压到 0.49。色相分布更难控（点名点缀色仍常被压成橙棕 70%+）——按「主色相与色温对上、点缀色可妥协」验收，别为色相占比反复消耗额度。
7. 结论=风格档案 + 已验证的复刻提示词，可直接用于做新技能（画质/色调/风格三段照抄）。
8. **「只学光影/色调，忽略内容」变体**（2026-10-22 实测《新古今大战秦俑情》38s）：用户明确说忽略画面内容时——①提问词只问色调（主色相/冷暖/饱和/明度）、光影（光源方向/数量/硬柔光/对比/阴影/高光）、色彩倾向（色罩/青橙对比/低饱和/胶片感）、氛围四段，**不描述主体**；②主体分析常把「可复刻提示词要点」截断，单独再问一次「只给可直接放进提示词的光影色调关键词串」；③产出的关键词串（如「冷蓝色调、低饱和度、柔光漫射、逆光透射、深邃阴影、高光朦胧、蓝绿色色罩、胶片颗粒感、低对比度、雾化光晕、沉浸式氛围、冷暖微对比」）直接当画质/色调/光影三段的底稿。
9. **一次学习→同源双技能**（2026-10-22 实测 picbpghost2 + picbpqinyong）：用户可能要「通用色调解读技能」（不限主题）+「主题命名技能」（限定该片氛围，如古风墓穴宿命）两版——两者**光影核心完全相同**，只差氛围段与主题限定；建第二版时在两边的经验小节互写「同源/关系」并说明差异，避免以后分不清该用哪个。

## 经验
- **⚠️ 克隆改造建新技能（性别版/室内外版/年代版）的高频流程与易漏点**（2026-10-25 批量实测 piczhboyin/out、picy2kgirlin/out、picglassout、picgirlsunny4→picgirlinside 系）：用户说「XX 换成男版」「场景换成室内/户外」「人物换成 Y2K 扮相」时——复制母版 SKILL.md 到新目录，逐项精确替换：①frontmatter name/description/version；②标题与创建说明（写明「源自 X 的男版/室外版/Y2K 版」）；③只动该动的段——**性别版**要替换模板里全部性别词与穿搭描述（美女→男生、高腰裙垫肩→皮夹克喇叭裤、珍珠耳环→腕表）；**室内/户外版**只换背景段（画风/姿势/文字三件套不动）；**⚠️ 克隆残留**（2026-10-26 pichybf 实测 8 处）：源技能「画风定义」表的**固定造型行** + 模板里的**表情句/构图句/边缘细节句**（橙框墨镜/撞色衬衫/串珠手链/蓝天/俏皮幸福洋溢等）会原样残留进新技能，与新人设（白发魔女等）直接冲突——克隆后 `grep` 源技能标志性造型词逐项清除，别只改发型和背景两处就以为干净了；④区别表行、技能族清单追加；⑤同步两端 diff + 索引行 + 选型依据键值对（先 grep 确认锚点存在再 replace）+ 必测。**用户对已定稿技能做「场景改为主题相关/自由配色」这类方向性迭代时，先出一张测试图确认效果再写进模板**（2026-10-25 picglassin/out「场景与主题相关」修改被用户弃用回滚实测：出了两张效果用户说放弃——先测图、确认后再落地模板，避免反复 patch + 回滚）。
- **画风绑定型技能的场景自由度三档**（2026-10-25 picglassin/out 三次迭代用户定稿）：①完全固定场景（如中式古典室内写死）②完全主题相关场景（场景类型也随主题变，古风→古典/朋友→咖啡厅）③**类型固定 + 道具随主题派生**——用户最终认可的是③：古典类型固定，场景内道具与装饰细节由主题派生（团扇/信笺/茶盏/花灯/喜字等）。机制：画风绑定型（Loish 古装等）场景类型完全脱离画风会破坏画风一致性，用户试了②后放弃回滚；**默认直接按③做，不要先做②再等回滚**。
- **命名规律 in/out（2026-10-25 用户定）**：室内版后缀 `in`、户外版后缀 `out`（piczhgirlin/out、piczhboyin/out、picy2kgirlin/out、picglassin/out）——同一画风按「室内/户外」拆双技能时用该后缀，索引行标注「源自 X 室外版」方便追溯。
- **命名规律 full（2026-10-26 用户定）**：全身展示版后缀 `full`（pichotpool→pichotpoolfull、picghost→picghostfull）——同一画风按「半身/全身」拆双技能时用该后缀；full 版只改构图（全身完整入镜），画风/扮相/表情/五元素全继承母版，索引行标注「全身变体版」；**full 版必带全身提亮口诀**（见五元素验收规则「全身构图/古宅暗调主题的提亮口诀」），否则暗调场景明度会被拖低。
- **⚠️ 用户发 RunningHub 单模型页链接要求「测试」时，先查该模型是否真可调用，不要用默认 image2.5 近似图冒充测试**：用户给的可能是 `runninghub.cn/model/public/<id>` 的 **LoRA/单模型页**（不是工作流、也不进 SKU）——按 runninghub-marketplace-search 的「LoRA 模型页：查找与测试」四步探测（模型页读类型/基础模型 → 搜模板 → 查 apiCallDemo 是否含 lora 字段 → 不行则告知需登录网页端）。**禁止拿基础模型的相似提示词出图就说「测过了」**：必须声明「这是基础模型近似效果，不是该 LoRA」。用户要的是真模型效果，假验证比承认做不到更伤信任。
- **⚠️ 同步脚本会静默保留「learn 进化版」技能**（sync_learn_skills.py 输出的「保留 learn 进化版 N 个」列表，含 picgirl/runninghub-marketplace-search 等）——default→learn 增量复制对它们**跳过**，改完 default 副本后 learn 本地仍是旧版。**更新这类技能后必须 `diff` 两端验证**，learn 落后则手动 `cp default→learn`；别只看 sync 脚本跑完就以为同步成功。
- **⚠️ 结构型画风遇到强叙事主题会被主题拽走**（2026-10-23 picbpwjw 测婚礼主题实测）：模板写「折叠春园/多重不可能阶梯/荷兰角/POV 塌陷」，主题换成婚礼后出图退化为常规欧式花园婚礼现场，错位阶梯与空间畸变全消失——结构词写全、排在场景描述前面也拦不住。**判定：POV/不可能空间/等距这类结构型画风在「婚礼/节日/庆典」等强叙事主题下遵循度最低；要保结构就换纯空间主题（庭院/回廊/书房），事件主题则如实标注漂移、跑一次定性，别连跑三次**。
- 主题=歌名时先定情感内核（深情/遗憾/炽热/轻盈），意象围绕内核，别逐句抄歌词。
- **用户主题疑似笔误时用正确字形，别把笔误原样写进标题**（2026-10-20 「华桥节」实测）：用户输入「华桥节」实为「华侨节」（同一主题之前已用正确字测过）——直接按正确词出图，并在回复里点明「你写的是 X，我按 Y 处理」；image2.5 通常也会自动渲染正确字形，但不要依赖它。
- 城市/品牌模板（picbp 等）改造：建筑细节与巨型特产元素换成当地真实特色，署名与配色为固定模板不随主题变。
- 用户会逐个测试主题（「测试主题：X picN」），流程=生成提示词→FAFO→t2i→发 MEDIA:，测两个主题后模板基本稳定。
- **「再来一张」变体偏好（2026-10-20 picgirly2k 实测）**：同一主题已出图后用户说「再来一张，XX 换成 YY」（如「美女换成黑长直」）——**只改人物属性描述（发型/发色/服装），画风/背景/标题/FAFO/版式全部保留**，重新出图+复核（主体属性是否按变体、标题与 FAFO 是否仍准确）；两图都发频道并保留服务器，回复时列出变体差异。
- 家族与 mv2 联动：mv2 歌词 MV 按歌词段主题调 picbp 出图（每段一张 880×1184），再走 musicvideo2 渲染——出图部分复用本技能规则（默认 app/FAFO/纯文本传参）。2026-10-12 实测跑通《K歌之王》《其实不想走》。

## mv2 出图联动要点（2026-10-12 实测；后续变体见下）
- **用户拍板的切换模式 = 均分每张一次**（N 张图 × 歌长/N 秒，每张只出现一次），不是歌词同步——同步是可选备选，未要求别默认用。生成 segments.json 时把每段时间设均分（start=round(i*per,2)），不要按歌词段时间。
- **批量出图**：8-10 张串行 t2i，每张 45-140s，总计 10-20 分钟——必须后台跑（background=true + notify），勿前台等 420s 超时。
- **渲染时长排期参考**（2026-10-26 《Stay With Me》322s 歌实测）：viz-render 全量 9672 帧 ≈ **73 分钟（约歌长×13.7，CPU 渲染每帧约 0.45s）**——渲染必后台跑 + notify；中断后重跑是全量重来（无断点续传），排期按全量估；纯音乐版无字幕，viz-render 完成后 ffmpeg 只转封装（`-c:a copy`）即可交付。
- 图生成（RunningHub 远程）可与另一首歌的渲染并行；但两首歌的**渲染要串行**（都是 CPU 密集，互拖）。
- 字幕与图片是两层独立时间轴：图片用均分时间轴，字幕用 whisper 歌词段时间（与歌声同步）——不要混用一个时间轴。
- **勿用 make_music_video.py ass 子命令做字幕**：段数>歌词行数时同一句重复显示；用 make_mv2_ass.py 或手写段映射。
- **渲染中途改图要杀进程重跑**：先 process_manage kill 当前 viz-render，替换图片后重新渲染（渲染产物是帧序列，图变了不会自动生效）。
- **首图=歌曲标题为主题**（用户偏好）：第一张图用纯歌名标题为主体创作，时长=视频开头到第一句歌词；其余段用歌词意境。
